# DOCX Generation Audit

Audit date: 2026-05-09

Scope: code inspection only, plus safe template-inspector and pytest commands. No application logic, tests, templates, or generated DOCX files were intentionally modified for this audit.

## 1. Executive summary

The system has two document-generation approaches:

- Template mode, the default path used by the command line and Streamlit UI. This copies user-corrected golden DOCX templates and then edits the copied output with `python-docx`.
- Generated mode, a fallback/comparison path. This rebuilds claim forms and attendance registers from scratch using `python-docx` tables, paragraphs, margins, fonts, and page setup helpers.

Claim forms in template mode are generated by copying `data/docx_templates/golden_claim_template.docx` to the output path, opening the copy, replacing selected paragraphs, filling a claim table, deleting or appending claim rows as needed, and saving the copy.

Attendance registers in template mode are generated as separate DOCX files, one per group/session-page chunk, under:

```text
data/generated/<year>/<month>/<staff_number>/registers/
```

The code does not generate a combined attendance register pack in template mode anymore, although the historical `attendance_path` value still points to a combined-style filename that is not expected to exist in template mode.

The golden templates are protected from direct modification in the main document workflow by a hash check in `app/document_generator.py`: the system hashes both golden templates before and after generation and raises an error if the hashes change. The template generator functions also copy the template to a separate output file before opening it. This is a useful guard, but not absolute protection against every possible accidental edit outside the generation workflow.

The likely reason formatting is still breaking is that the current "copy template and replace text" approach is not truly layout-neutral. The code still:

- Replaces whole paragraph text, including paragraphs that rely on tabs for visual alignment.
- Clears cell content by rewriting runs.
- Deletes claim table rows.
- Appends copied rows when capacity is insufficient.
- Saves DOCX files through `python-docx`, which can normalize or rewrite Word XML.
- Relies on fixed paragraph indexes and table coordinates instead of explicit placeholders or content controls.

So the current implementation mixes a copy-template approach with structural edits and text replacement that can disturb the manually corrected layout.

## 2. Full document generation workflow

### A. Streamlit UI path

The Streamlit document generation page is implemented in `app_ui/streamlit_app.py`, function `page_document_generation()`.

Current UI flow:

1. User opens the local Streamlit app:

   ```powershell
   streamlit run app_ui/streamlit_app.py
   ```

2. User selects `Document Generation` from the sidebar.

3. `page_document_generation()` renders:
   - lecturer selector via `lecturer_selector("docs_lecturer")`
   - year input
   - month selector
   - layout mode selector with `template` and `generated`
   - `Generate draft documents` button

4. When clicked, the UI calls:

   ```python
   generate_monthly_documents(
       lecturer_id,
       int(year),
       month,
       allow_clashes=False,
       layout_mode=layout_mode,
       strict_template=True,
   )
   ```

5. The UI does not generate DOCX itself. It delegates to `app/document_generator.py`.

6. On success, the UI displays:
   - output folder
   - verification checklist path
   - claim path
   - each attendance register path from `result["attendance_paths"]`

7. If missing-template errors occur, the UI catches them and displays:

   ```text
   Missing DOCX template. Copy the approved templates to data/docx_templates/.
   ```

Files read through this path:

- SQLite database at `data/pt_claims.db`
- Golden templates, if `layout_mode="template"`:
  - `data/docx_templates/golden_claim_template.docx`
  - `data/docx_templates/golden_attendance_register_template.docx`

Files written through this path:

- `data/generated/<year>/<month>/<staff_number>/claim_form_<staff>_<year>_<month>.docx`
- `data/generated/<year>/<month>/<staff_number>/registers/register_<staff>_<course>_<group>_<year>_<month>_pN.docx`
- `data/generated/<year>/<month>/<staff_number>/verification_checklist_<staff>_<year>_<month>.xlsx`

### B. Command-line path

Command:

```powershell
python -m app.document_generator --lecturer-id 1008977 --year 2026 --month 4 --layout-mode template --strict-template
```

Important function call order:

1. `app.document_generator.main()`
2. `generate_monthly_documents(...)`
3. `resolve_lecturer_id(...)`
4. `generate_monthly_sessions(...)` from `app/session_generator.py`
5. `detect_clashes(...)` from `app/validators.py`
6. `output_directory(...)` determines:

   ```text
   data/generated/<year>/<month>/<staff_number>/
   ```

7. If the output directory already exists, `shutil.rmtree(out_dir)` deletes it.
8. If clashes exist and `allow_clashes=False`:
   - generate only verification checklist
   - return with `documents_generated=False`
9. In template mode:
   - hash `CLAIM_TEMPLATE_PATH`
   - hash `ATTENDANCE_TEMPLATE_PATH`
   - call `generate_template_attendance_register_pack(...)`
   - call `generate_template_claim_form(...)`
   - hash both templates again
   - raise `RuntimeError` if template hashes changed
10. Generate verification checklist via `generate_verification_checklist(...)`
11. Return result dictionary.
12. CLI prints generation summary and file details.

In generated mode:

1. `generate_layout_attendance_register_pack(...)` from `app/attendance_register_generator.py`
2. `generate_layout_claim_form(...)` from `app/claim_form_generator.py`

Generated mode rebuilds the layouts from scratch.

## 4. Template handling

Expected template files:

```text
data/docx_templates/golden_claim_template.docx
data/docx_templates/golden_attendance_register_template.docx
```

Older template names exist in requirements/history:

```text
data/docx_templates/claim_template.docx
data/docx_templates/attendance_register_template.docx
```

Current default code uses the golden templates:

- `app/template_claim_generator.py`
  - `CLAIM_TEMPLATE_PATH = DOCX_TEMPLATES_DIR / "golden_claim_template.docx"`
- `app/template_register_generator.py`
  - `ATTENDANCE_TEMPLATE_PATH = DOCX_TEMPLATES_DIR / "golden_attendance_register_template.docx"`

The current template mode does not silently fall back to older templates. If a golden template is missing, `require_template(...)` raises a `MissingDocxTemplateError` with a message asking the user to copy the user-corrected template into `data/docx_templates/`.

The code copies templates before editing:

- Claim: `shutil.copy2(template, output)`, then opens `Document(output)`.
- Register: `shutil.copy2(template_file, page_output)` for each generated register file, then opens `Document(page_output)`.

Golden template hash check:

- `app/document_generator.py` hashes both golden templates before generation.
- It hashes them again after generation.
- It raises `RuntimeError` if the before/after hash dictionaries differ.

Can the golden templates still be modified accidentally?

- During the main `generate_monthly_documents(...)` flow, the hash check should catch accidental template mutation.
- Direct calls to `generate_template_claim_form(...)` or `generate_template_attendance_register_pack(...)` copy the template before editing, so they should not edit the template directly.
- However, nothing stops a developer or external process from opening and modifying the golden template outside this workflow.

## 5. Claim form generation mechanism

### Detail insertion

`generate_template_claim_form(...)`:

1. Validates non-empty sessions.
2. Calls `require_template(...)`.
3. Copies the golden claim template to the output path.
4. Opens copied output with `Document(output)`.
5. Calls `map_claim_template(document)`.
6. Calls `_fill_claim_particulars(...)`.
7. Calls `_fill_claim_rows(...)`.
8. Saves the output.

`map_claim_template(document)`:

- Finds the largest table in the document and treats it as the claim table.
- Finds the claim header row by searching for both `lecture` and `office use`.
- Maps paragraphs by searching paragraph text:
  - `Name & Surname`
  - `Highest qualification`
  - `Personnel Number`
  - `Identity / Passport Number`
  - `Address`
  - `Level of training offered`
  - `HR`
  - `Course/Post`

The inspected golden claim template currently has:

- 34 paragraphs
- 1 table
- table 0 has 102 rows x 10 columns
- claim header row: 0
- claim data row range: 1 to 101

### Lecturer details

`_fill_claim_particulars(...)` uses the first row of `sessions_df` and replaces mapped paragraphs:

- `Name & Surname: <lecturer_name>`
- `Highest qualification: ... Budget Allocation: ...`
- `Personnel Number: ... Tariff per hour: ...`
- `Identity / Passport Number: ... PAYE No.: ...`
- `Address: ... Tel. no.: ...`

This is not cell-based replacement. It is whole-paragraph replacement using strings with tab characters. That makes layout dependent on tab behavior and paragraph/ruler settings.

### Title selection

Current template claim generator does not appear to programmatically mark title checkboxes. It also does not explicitly clear title marks. The generated fallback `claim_form_generator.py` does title marking, but the golden-template generator does not.

### Training-level selection

The current golden-template generator sets only this paragraph:

```text
Level of training offered (indicate with an X):
```

It does not currently mark the Part-time option in code. Inspector output says the training-level option labels are drawing/textbox content in the template; the paragraph label is separate. This is likely why earlier attempts to append `Part-time X` caused duplication and layout drift.

The current code prevents the specific duplicated label by overwriting the level paragraph with only the label text. Tests check the forbidden strings are absent. That is a text-level fix, not a visual assertion.

### HR total hours

The code rewrites the mapped `HR` paragraph:

```python
PARTICULARS OF CLAIM\t\t\t\t\tHR â€“ TOTAL HOURS CLAIMED: <hours>
```

Important risk: the source file contains a proper en dash in inspection output (`HR – TOTAL HOURS CLAIMED`), but source code shows mojibake (`HR â€“ TOTAL HOURS CLAIMED`). Tests also look for the mojibake form. This does not necessarily break layout, but it is a text/encoding quality issue.

### Course/Post and Faculty/Department

`_course_post(...)` returns joined sorted course codes:

```text
CUS411S & ICT521S
```

`_faculty_department(...)` returns joined unique departments only, not faculty plus department:

```text
Informatics
```

Then `_fill_claim_particulars(...)` writes:

```text
Course/Post: <course_codes>   Faculty/Department: <departments>
```

This is whole-paragraph replacement and uses tabs/spaces for layout.

### Claim rows

`_fill_claim_rows(...)`:

- Uses the mapped claim table.
- Uses columns:
  - 0 number
  - 1 date
  - 2 lecture
  - 3 consultation
  - 4 department/board
  - 5 time
  - 6 hours
  - 7 tariff
  - 8 cents
  - 9 office
- Sorts sessions by `group_name`, `session_date`, `start_time`.
- Groups by `group_name`.
- Restarts numbering for each group.
- Puts `X` in the lecture column.
- Puts group name in the consultation column only on the first row for each group.
- Formats date as `dd/mm/yyyy`.
- Formats time as `HH:MM-HH:MM`.
- Formats whole hours as whole numbers.
- Puts tariff in N$ and `00` in cents.

### Row reuse/deletion/copying

The code calculates:

```python
target_rows = len(records) + 2
```

If the template has too few rows, it appends copies of an existing row using raw XML.

If the template has too many rows, it deletes rows from the table with:

```python
table._tbl.remove(row._tr)
```

Then it clears all remaining target rows and fills generated records.

This means old sample rows are not merely replaced in place. Many rows can be deleted. For Maria's 69 sessions, the expected target is 71 rows, plus the header makes 72 rows in tests. The test asserts that table row count becomes 72.

### Signature block protection

The signature block is not inside the claim table according to current behavior; it is in document paragraphs after the table. The code protects it indirectly by deleting only table rows. However, deleting many table rows can still change where the signature block lands visually.

### Why the claim layout may shift

Likely causes:

- Whole paragraph replacement removes original run structure.
- Right-side values are positioned by tabs and spaces, not stable cells/content controls.
- Deleting rows can alter table height, pagination, and relationship to following paragraphs.
- Appending rows copies raw row XML but the copied row may carry unexpected formatting.
- Saving through `python-docx` may rewrite some XML.
- Title and training option areas are not robustly mapped if they are drawings/textboxes.

### Why Part-time duplication happened

Earlier code likely wrote training-level text after the label or attempted to mark the option by altering the same paragraph. The current code avoids this by replacing the label paragraph with only:

```text
Level of training offered (indicate with an X):
```

Current tests check that `Part-time X`, `Level ...: Part-time`, and `Part-ti` do not appear. That confirms text absence; it does not confirm visual correctness of the checkbox area.

## 6. Attendance register generation mechanism

### Register splitting

`generate_template_attendance_register_pack(...)` groups sessions by:

```python
["faculty", "department", "course_name", "course_code", "group_name", "campus"]
```

For each group, it sorts by `session_date`, `start_time`.

It then chunks sessions by the number of session columns detected in the template.

The inspected golden attendance template has:

- 10 paragraphs
- 1 table
- table 0 has 16 rows x 9 columns
- DATE row: 1
- TIME row: 2
- student row range: 3 to 15
- session columns: `[4, 5, 6, 7, 8]`
- number of session columns: 5

So each register page can hold 5 session dates/times. More than 5 sessions creates another separate DOCX file for the same group with suffix `_p2`, `_p3`, etc.

### Separate vs combined registers

Current template mode creates separate DOCX files. It does not combine registers into one DOCX.

The historical output path passed into `generate_template_attendance_register_pack(...)` is still something like:

```text
attendance_registers_<staff>_<year>_<month>.docx
```

But template mode uses only its parent folder and creates:

```text
registers/register_<staff>_<course>_<safe_group>_<year>_<month>_pN.docx
```

Tests assert the combined attendance path does not exist in template mode.

### Date/time cells

`map_register_template(...)` finds the first row containing `date` and the first row containing `time`.

It assumes session columns are:

```python
range(4, max_column_count)
```

The mapping output confirmed columns 4 to 8.

Dates are formatted as `dd-mm-yy`, e.g. `09-04-26`.

Times use `format_time_range(...)`, e.g. `10:30-12:30`.

### Student rows and columns

The code assumes:

- number column: 0
- surname column: 1
- initials column: 2
- student number column: 3

The inspector confirms these coordinates on the golden attendance template.

`_student_rows(...)` reads `surname`, `initials`, and `student_number` from the database. If surname is missing but full name exists, it derives a fallback.

`get_students_for_group(...)` in `attendance_register_generator.py` queries:

- `group_enrolments`
- `students`
- `student_groups`
- `courses`

It filters active enrolments/students and matches `group_name` plus `course_code`. It orders by surname, initials, student number.

### Footer fields

The attendance generator maps footer paragraphs by fixed indexes:

- paragraph 7: signature values
- paragraph 8: signature labels

`_fill_paragraphs(...)` writes paragraph 7 as:

```text
<lecturer_name>\t _______________________________\t\t<staff_number>\t
```

This is not cell-based; it uses tabs in a whole paragraph. If the template relies on specific tab stops or Word layout behavior, this is a risk.

### Page breaks and combining

Template mode:

- Does not append multiple pages into a single DOCX.
- Does not add page breaks in the generated register files.
- Each file is a fresh copy of the golden template.

Generated fallback mode:

- Builds a combined attendance pack.
- Inserts page breaks between chunks.
- Adds visible Register ID.

### Row handling

Current template register generation:

- Clears all student rows in the existing template table.
- Fills student rows.
- Appends rows only if there are more students than available template rows.
- Does not delete unused rows in current code.

The golden attendance template has 13 student rows, row 3 to row 15. The current demo data has 12 students plus one blank row in the template, so tests pass with 16 total table rows. If fewer than 12 students exist, leftover rows are cleared but still physically present.

### Why one register may appear below another on the same page

This should not happen in current template mode because registers are separate files. It can happen in:

- generated fallback mode, if page breaks fail or are not interpreted as expected;
- old versions that appended multiple template pages into a single DOCX;
- manually combining individual register outputs later;
- a stale old combined output file being opened instead of the current `registers/` output.

### Why cell alignment or text placement may shift

Likely causes:

- `_set_paragraph_text(...)` rewrites paragraph runs but does not preserve all run-level formatting.
- `_set_cell_text_preserve(...)` clears extra paragraphs in a cell.
- The function accepts `font_size` and `alignment` but currently does not apply them in `_set_paragraph_text(...)`.
- Header and footer paragraphs are whole-paragraph replacements using tabs and long underscores.
- `python-docx` save can normalize Word XML.

## 8. Formatting risk analysis

### Clearing cell text

Where:

- `app/template_claim_generator.py`, `_set_cell_text_preserve(...)`
- `app/template_register_generator.py`, `_set_cell_text_preserve(...)`
- `app/docx_utils.py`, `set_cell_text(...)`

Risk:

- Can remove multiple paragraphs in cells.
- Can remove run-level styling or split-run formatting.
- Can disturb cells that rely on multiple runs, drawings, fields, or line breaks.

Current implementation:

- Risky for exact visual preservation.

### Replacing paragraph runs

Where:

- `template_claim_generator._set_paragraph_text(...)`
- `template_register_generator._set_paragraph_text(...)`

Risk:

- Replaces first run text and clears subsequent runs.
- Does not preserve original multi-run styling.
- Does not reliably apply supplied `font_size` or `alignment` in these functions.
- Whole-paragraph replacement with tabs is layout-fragile.

Current implementation:

- Risky, especially for claimant details and footer.

## 10. Alternative approaches

### A. Continue with python-docx and improve template placeholders

Benefits:

- Minimal new dependency.
- Current codebase already uses `python-docx`.
- Can keep DOCX editable.

Risks:

- Still fragile if relying on paragraph indexes and tabs.
- Visual fidelity remains difficult without rendering tests.

Fit:

- Reasonable short-term if templates are simplified and placeholders are explicit.

Layout preservation:

- Better than current only if replacement is limited to placeholders inside stable runs/cells.

### B. DOCX templates with explicit placeholders like `{{LECTURER_NAME}}`, `{{CLAIM_ROWS}}`, `{{REGISTER_ROWS}}`

Benefits:

- Removes guesswork from paragraph/table mapping.
- Easier to audit and test.
- Reduces accidental replacement of wrong content.

Risks:

- Requires creating clean templates with placeholders.
- Repeating rows still need careful handling.

Fit:

- Strong fit. This is the clearest upgrade from the current approach.

Layout preservation:

- Likely better than current fixed-index/tab replacement.

### C. Use `docxtpl`

Benefits:

- Built for templated DOCX generation.
- Supports placeholders and table loops.
- Keeps Word templates editable.

Risks:

- Adds dependency.
- Complex Word layouts, textboxes, drawings, and merged tables can still be tricky.
- Requires template redesign using Jinja-style placeholders.

Fit:

- Good fit if DOCX output must remain editable.

Layout preservation:

- Usually better than manual `python-docx` mapping, if templates are designed carefully.

### D. Generate HTML/CSS and convert to PDF/DOCX

Benefits:

- HTML/CSS can be easier to control for printed layout.
- Browser rendering can be visually tested.

Risks:

- DOCX conversion fidelity may be poor.
- Adds conversion tooling.
- User requested editable Word outputs historically.

Fit:

- Better for PDF-first output than editable DOCX.

Layout preservation:

- Good for PDF, uncertain for DOCX.

### E. Generate PDF directly

Benefits:

- Strong control over final printed appearance.
- Avoids Word layout drift.

Risks:

- Not editable in Word.
- User explicitly said not to generate PDFs in current phases.
- Official workflow may require Word documents.

Fit:

- Possible later if final submission can be PDF.

Layout preservation:

- Much better for final visual output, worse for editability.

### F. Use Excel templates instead of Word

Benefits:

- Attendance registers are table-heavy and may fit Excel naturally.
- Better cell grid control.
- Easier row/column filling.

Risks:

- Institutional templates are currently Word.
- Claim form may not translate perfectly.

Fit:

- Strong for attendance registers, moderate for claim forms.

Layout preservation:

- Strong if official forms can be Excel or printed from Excel.

### G. Microsoft Word mail merge or content controls

Benefits:

- Word-native templating.
- Content controls are robust anchors.
- Can preserve layout well.

Risks:

- Automation may require Word/COM on Windows or more complex tooling.
- Harder to run headlessly.

Fit:

- Good if this remains a Windows/local office workflow.

Layout preservation:

- Potentially excellent.

### H. Fillable form approach

Benefits:

- Fixed layout with fields.
- Reduces layout changes.

Risks:

- Dynamic claim rows and variable register pages are harder.
- May need PDF forms or Word content controls.

Fit:

- Good for fixed claimant details, less ideal for variable session rows.

Layout preservation:

- Excellent for fixed sections, limited for dynamic rows.

## 11. Recommendation from code audit only

Preliminary recommendation:

Do not keep extending the current fixed-index, tab-based replacement strategy. It is too fragile for a document whose visual layout is critical.

Recommended direction:

1. Keep the backend session, clash, student, and verification logic.
2. Split DOCX generation into a clearly isolated document module.
3. Replace fixed paragraph-index replacement with explicit placeholder-based DOCX templates.
4. Prefer either:
   - a disciplined `python-docx` placeholder replacement approach, or
   - `docxtpl` if table row loops can be cleanly expressed.
5. For attendance registers, seriously consider Excel templates if the institution accepts them, because the output is fundamentally tabular.

Do not switch to PDF yet unless editable Word output is no longer required.
